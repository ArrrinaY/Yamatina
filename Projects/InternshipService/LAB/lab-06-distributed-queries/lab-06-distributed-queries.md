## 1. Вспоминаем архитектуру

После шардирования (Лабораторная №5):

```
Backend
  │
  Router (hash(candidate_id) % 3)
  ┌────────┼────────┐
  ▼        ▼        ▼
 Shard 0  Shard 1  Shard 2
```

- Shard key: **candidate_id**.
- 3 шарда, одинаковые таблицы `applications` (~33 286 / 33 440 / 33 274 строк).
- Для каждого `candidate_id` «владеет» ровно один шард.

## 2. Single-shard query

Запрос с условием по shard key:

```sql
SELECT count(*) FROM applications WHERE candidate_id = 12345;
```

Результаты (выполнены на всех 3 шардах, `results/01_single_shard_and_aggregation.txt`):

| Шард | candidate_id=12345 |
|------|-------------------|
| Shard 0 | 0 |
| Shard 1 | 1 |
| Shard 2 | 0 |

`candidate_id=12345` находится на **shard 1** (`hash % 3 = 1`).

**Почему запросу не нужно обращаться к другим шардам:**
Данные конкретного `candidate_id` хранятся только на одном шарде — том,
который дал этот `hash % 3`. Остальные шарды гарантированно не
содержат данных этого кандидата, поэтому точный ответ даёт обращение
только к «своему» шарду. Остальные шарды вернут 0 строк (безопасный,
но неверный ответ, если не знать, куда направлять запрос).

```sql
SELECT (hashtext(12345::text) & 2147483647) % 3 AS shard_index;
-- 1
```

Это аналогично нашему сервису: `GET /applications/candidate/{id}` в
распределённой версии должен направлять запрос только на один шард,
а не стучаться во все.

## 3. Агрегирующий запрос

COUNT по статусам **на каждом шарде** (`results/01_single_shard_and_aggregation.txt`):

| Шард | status=0 | status=1 | status=2 | status=3 | всего строк |
|------|----------|----------|----------|----------|-------------|
| Shard 0 | 8388 | 8336 | 8264 | 8298 | 33286 |
| Shard 1 | 8314 | 8391 | 8364 | 8371 | 33440 |
| Shard 2 | 8298 | 8273 | 8372 | 8331 | 33274 |
| **Сумма** | 25000 | 25000 | 25000 | 25000 | **100 000** |

**Глобальный ответ** собирается на уровне backend (роутер бэкенда):

- Shard 0 → `{(0, 8388), (1, 8336), (2, 8264), (3, 8298)}`
- Shard 1 → `{(0, 8314), (1, 8391), (2, 8364), (3, 8371)}`
- Shard 2 → `{(0, 8298), (1, 8273), (2, 8372), (3, 8331)}`
- **Итог** → `{(0: 25000), (1: 25000), (2: 25000), (3: 25000)}`, сумма = **100 000**.

**Ответы на вопросы:**

1. Можно ли выполнить такой запрос только на одном шарде?
   Нет — ответ будет частичным (доля по этому шарду, ~¼ от полного).
   Вернёт неверное значение для клиента.

2. Где должны объединяться результаты?
   На уровне backend-сервера (роутер): собирает ответы со всех шардов,
   агрегирует (SUM для COUNT, UNION для строк, Merge Sort для сортировки)
   и возвращает клиенту итоговый результат.

3. Что происходит со временем выполнения при увеличении количества шардов?
   Растёт: нужно отправить запрос на каждый шард (сетевой трафик),
   дождаться ответов со всех шардов (latency = latency slowest node +
   объединение результатов (CPU + RAM на бэкенде). При N → 3N удваивается

4. JOIN между шардами

В нашем сервисе JOIN взят как пример:
- `applications.vacancy_id` → `vacancies.id`.
- JOIN в приложении (`results/02_join_demo.txt`):

```sql
SELECT a.id, a.candidate_id, a.vacancy_id, v.title
FROM applications a
JOIN vacancies v ON a.vacancy_id = v.id
ORDER BY a.applied_date DESC LIMIT 5;
```

**Результаты:**

| Шард | vacancies? | JOIN? |
|------|------------|-------|
| Shard 0 | есть (создан вручную для теста) | ✅ 5 строк |
| Shard 1 | нет | ❌ ERROR: relation "vacancies" does not exist |

**В реальной распределённой архитектуре:**
Если `vacancies` тоже шардирована (по `vacancy_id` или иному ключу),
то JOIN `applications JOIN vacancies` возможна либо:
- Если таблицы шардированы **по одному ключу** (co-location) —
  JOIN выполняется локально на одном шарде.
- Если шардирования разное — сервис должен делать scatter-gather для
  связанных данных (медленно, correctness проблемы).

**Ответы на вопросы:**

1. Что произойдёт, если связанные записи находятся на разных шардах?
   Запрос ломается: либо падает ошибкой «таблица не существует»,
   либо возвращает частичные данные (если сервис игнорирует и показывает
   «неполную» — тут опасность business logic flaw).

2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?
   Нет — если таблицы на разных шардах. Каждый шард — отдельный экземпляр БД,
   к нему нельзя «доключиться» к другому шарду в рамках одного запроса.

3. Какие данные пришлось бы передавать между шардами?
   При distributed join сервис должен достать candidate_id'ы из shard1/shard2,
   а затем выполнить lookup в shard_vacancies по этим id'ам. То есть
   передаются идентификаторы (int'ы), но всё равно это сетевая операция
   для каждого candidate_id (count * 1 round-trip per row).

4. Можно ли выбрать shard key так, чтобы этот JOIN чаще выполнялся
   внутри одного шарда?
   Да. Если shard key = `vacancy_id`, то все заявки к одной вакансии
   попадут на один шард вместе с самой вакансией — JOIN локальный.
   Но тогда single-shard query по `candidate_id` (главный запрос сервиса)
   разрушится: нужно scatter-gather по всем шардам.
   Обычно выбирают ключ по наиболее частым запросам.

5. ORDER BY + LIMIT

Проблема: получить **топ-10 самых свежих заявок** сервиса
(`ORDER BY applied_date DESC LIMIT 10`).

**Попытка 1 — взять только с одного шарда:**
Берём shard 0, ORDER BY ... LIMIT 10 → 10 записей. Но глобально
самые свежие заявки могут быть на shard 1 или shard 2 — мы пропускаем
2/3 данных! Итоговый топ **неверный**.

**Правильная стратегия (merge-топ):**
1. На каждом шарде: `SELECT ... ORDER BY applied_date DESC LIMIT 10;`
2. Получить 10 + 10 + 10 = 30 строк.
3. Объединить (merge sort по applied_date) и взять LIMIT 10.

**Результаты merge (из `results/04_orderby_merge.txt` выше):**
Мы помним, что на каждом шарде топ-10 — это разные id (1-35),
а глобально топ собирается из лидеров каждого шарда. Например:

| id | candidate_id | applied_date           | shard |
|----|---------------|------------------------|-------|
| 1  | 1             | 2026-09-16 22:00:43   | 0     |
| 2  | 2             | 2026-09-16 21:59:43   | 1     |
| 3  | 3             | 2026-09-16 21:58:43   | 1     |

(на практике с 100000 записей — результатная таблица выше)

**Почему недостаточно получить первые 100 записей только с одного шарда:**
- Пропускаем другие шарды — глобальный top-100 будет **неверным**.
- Клиент получит неполный ответ — бизнес-логика ожидает «последние 100
  заявок» как актуальный, а мы отдаём только сегмент одного шарда.
  Это ошибка (partial response → неверные решения).

   не увидит свои заявки — запрос вернёт ошибку или timeout.

   количество запросов и latency стал доминироваться slowest shard.
