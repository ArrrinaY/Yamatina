# Контрольные вопросы — Лабораторная №4

## 1. Чем Primary отличается от Replica?

Primary принимает все операции записи (INSERT/UPDATE/DELETE) и генерирует WAL. Replica — копия Primary: работает в режиме recovery, только проигрывает полученный WAL и обслуживает чтение (hot standby). Запись на Replica запрещена.

## 2. Почему запись выполняем на Primary?

Только Primary является источником истины и генерирует WAL. Запись на несколько узлов потребовала бы распределённого консенсуса (multi-master). Единая точка записи даёт простой и предсказуемый механизм согласованности: все изменения рождаются в одном месте.

## 3. Как изменение из Primary попадает на Replica?

Транзакция коммитится на Primary → изменение записано в WAL → WAL sender на Primary читает WAL и отправляет по сети → WAL receiver на Replica принимает и записывает локально → процесс восстановления (startup) проигрывает изменения. Состояние видно в `pg_stat_replication` (state = streaming).

## 4. Что такое WAL в контексте репликации?

Write-Ahead Log — журнал, в который PostgreSQL сначала пишет описание изменений, прежде чем применять их к страницам данных. В streaming replication WAL используется как транспорт изменений: Primary отправляет сгенерированные записи WAL, Replica воспроизводит их у себя.

## 5. Что такое replication lag?

Отставание Replica от Primary — объём WAL (или время), который Primary уже зафиксировал, а Replica ещё не воспроизвела. Измеряется `pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)` и колонками `replay_lag` в `pg_stat_replication`.

## 6. Почему SELECT сразу после INSERT на Replica может увидеть старые данные?

INSERT коммитится на Primary и приложение получает управление, не дожидаясь Replica (репликация асинхронная). Если в этот момент читать с Replica, WAL с этим INSERT ещё может не быть воспроизведён — запрос вернёт состояние на прошлый момент времени. Это следствие replication lag.

## 7. Что именно масштабируется при Read Scaling?

Не скорость одного SQL-запроса, а способность системы обслуживать больше чтений суммарно: N экземпляров могут параллельно исполнять N независимых SELECT-потоков. Отдельный запрос не становится быстрее, но общий read-трафик делится между узлами (balance read load), и тяжёлые отчёты не мешают записи.

## 8. Почему наличие Replica не отменяет индексы и оптимизацию SQL?

Каждый запрос на Replica выполняется по тем же правилам: без индексов — Seq Scan по всей таблице. Реплика лишь умножает количество «железок», но каждый узел остаётся обычным PostgreSQL с теми же планами. Плохой запрос просто станет плохим на всех репликах параллельно.

## 9. Расскажите про CAP-теорему

В распределённой системе из трёх свойств — Consistency (все узлы видят одни данные), Availability (каждый запрос получает ответ), Partition tolerance (система работает при разрыве сети) — можно гарантировать только два. Сетевые разделения неизбежны, поэтому выбор стоит между C и A. Асинхронная репликация — это классический выбор в пользу доступности и производительности: Primary отвечает сразу, Replica может временно отставать (итоговая согласованность, eventual consistency). Синхронная репликация дала бы строгую согласованность ценой доступности и задержки записи.
